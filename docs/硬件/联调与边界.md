# 硬件联调与边界

## 不可修改的边界

EasyMacBord 是现有 EasyInput V2.0 的 macOS 消费端。本仓库不修改 ESP32-S3 固件、GPIO、BOOT、GPIO8 共享电源、Flash 分区、USB HID 标识、蓝牙配置通道定义、VID/PID、HID 描述符和自定义 GATT 定义。

正常模式 USB 是 HID，不是 CDC 串口。看不到串口不能作为设备失败结论。烧录、复位、`idf.py flash`、`esptool` 和设备识别不在本仓库工作流内。

## 联调前置

1. 使用已通过上游验证的 EasyInput V2.0 固件。
2. 先核对 USB `VID 0x303A / PID 0x1006`，以及蓝牙配置服务 `7D2F4D10-6F6B-4A2D-8B01-6D4653320001` 与写入、状态特征。任一不符即停止本仓库联调并标记 `UNKNOWN`。
3. 记录设备是否能以 USB HID 或蓝牙配置通道被发现；不记录完整 MAC、序列号或 USB 拓扑。
4. 使用“计算器”验证 Host Action 实际打开，使用 TextEdit 验证固定文本、快捷键、复制和粘贴。
5. 同步后核对 `0x11 / kind 0x03` 确认的 phase、saved、bytes 和 CRC。
6. T05 状态读取仅使用上游已有合同：以 USB Feature Report `0x13` 发送 16 字节 `S3R v1` 请求，接收 `0x11 / kind 0x04` 分片状态响应。验证 request ID、分片、总长度和 CRC 后才消费 `ai_keyboard.config_status.v1`；该测试不改写设备状态。
7. 若状态 JSON 没有 `capabilities.semantic_actions=true`，记录为 `UNKNOWN` 或未声明，不为设备语义动作、灯光或音乐律动补发新命令。语音和编辑按住说话还需观察 `ptt_hotkey` 与 `edit_ptt_hotkey` 是否实际返回；字段缺失保持“设备未确认”。灯光和律动仍需要单独的、版本化设备控制合同，T05 不创建该合同。

## 故障定位顺序

设备不可见 → 连接通道 → 状态请求/响应校验 → 配置写入 → 保存确认 → 能力状态 → Host Action 消息 → UUID 映射 → macOS 权限 → 目标应用执行。

任何一层没有证据时，保留现场并记录失败层；不重烧录、不手写 UUID、不通过重复同步制造“成功”。
